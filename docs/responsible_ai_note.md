# Responsible AI note

EXL × UCD Data & AI Hackathon 2026 · Challenge 03 · Team Agent Zero

## Data used

**Synthetic only.** Every policy, claim and premium record in this project
is generated by `data/generate_synthetic_data.py`, a seeded (`seed=42`)
Python script — no real, production, or personal insurer data was used or
accessed anywhere in this project. Policy/customer/claim IDs are
sequential synthetic identifiers (`POL000001`, `CUST000042`, ...), not
derived from any real person or entity. See `data/README.md` for the full
schema.

The 10 "legacy" T-SQL/SAS jobs themselves were also written by us for this
project, to carry realistic legacy quirks (hardcoded dates, implicit
fan-out joins, BY-group processing) — they do not represent, and were not
derived from, any real insurer's actual code.

## Privacy and security safeguards

- No real data in the repo, in agent prompts, or in any CI job — agent
  prompts only ever contain our own synthetic legacy code and synthetic
  data schemas, never records.
- Everything runs locally: synthetic data generation, PySpark jobs, the
  reconciliation engine, and the discovery/translation/test-gen agents.
  Nothing is uploaded to a third-party service beyond the `claude` CLI
  calls themselves (Anthropic, under Aditya's existing Claude Code
  subscription — no separate API key, no data retention arrangement beyond
  Anthropic's standard API terms).
- `.gitignore` excludes generated data/baseline CSVs from the repo, and
  `gitleaks` runs on every commit (locally via pre-commit, and again in CI)
  to catch any accidentally-committed secret.
- Every agent-generated file goes through a GitLab merge request and is
  reviewed (by a human and by a separate Claude Reviewer CI job) before
  being merged — no agent output reaches `main` unreviewed.

## Known bias and limitations

- **Synthetic-data bias:** the data generator's distributions (claim
  frequency, product-line mix, regional spread) are illustrative choices,
  not calibrated to any real insurer's actual portfolio. Any metric
  computed from this data (loss ratios, aging buckets) is representative
  of the *pipeline's correctness*, not of real business performance.
- **SAS baseline is not SAS-verified.** SAS cannot run in this
  environment. Every baseline for the 3 `.sas` jobs is an independent
  Python/pandas re-implementation of the program's documented logic, not
  output from a real SAS engine. A PASS for a SAS-derived job means the
  migrated PySpark job matches a verified-equivalent reference
  implementation — it does **not** mean it was checked against the actual
  legacy SAS runtime. This is stated on every such reconciliation report
  (`reconciliation/reports/*.md`) and in `legacy/baselines/MANIFEST.md`,
  not just here.
- **T-SQL baselines are mostly reference-implementation too.** Only one of
  7 T-SQL jobs (`claims_monthly_summary`) was additionally validated
  against a real SQL Server 2022 instance (538/538 rows matched exactly);
  the other 6 rely on the same pandas reference-implementation approach as
  the SAS jobs, for the same reason (time budget, not a technical
  limitation of SQL Server itself — see `legacy/baselines/MANIFEST.md`).
- **LLM translation can be wrong, and was, twice, tonight.** The
  translation agent's first attempt at `claims_status_rollup_by_quarter`
  had an ambiguous-column bug; a reference-implementation bug in
  `policy_portfolio_rollup` was also found and fixed. Both were caught by
  the reconciliation engine and/or code review, not assumed away — this is
  the entire point of the reconcile-and-review step, and is why no agent
  output in this project counts as "done" until it passes both.
- **Small sample, short build.** 10 jobs, ~22k total synthetic rows, built
  in one evening. Findings here (time saved, reconciliation pass rate)
  should be read as a prototype proof-of-concept, not a statistically
  powered result — see `docs/time_saved.md` for exactly which numbers are
  measured vs. assumed.

## AI tools used (declared)

- **Claude Code**, invoked headlessly (`claude -p`) — powers:
  - the discovery/lineage agent (`agents/discovery.py`)
  - the translation agent (`agents/translate.py`)
  - the test-generation agent (`agents/testgen.py`)
  - the Claude Reviewer CI job that reviews every merge request
  - (this document, the architecture diagram, and the rest of the
    submission pack were drafted with Claude Code as a general coding
    assistant, same as the rest of this repo)
- **No other AI/ML model, API, or service** is used anywhere in this
  project — no separate embeddings model, no third-party ML API, no
  additional LLM provider.

## Safeguards against unverified claims

Per this project's own `CLAUDE.md` convention: no report, doc, or deck
slide may present a reconciliation result as verified against the legacy
engine when it is actually verified against a reference implementation.
This note, the reconciliation reports, and the deck all draw that
distinction explicitly rather than letting "PASS" imply more than it does.
